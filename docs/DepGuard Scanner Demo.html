Software Dependency Vulnerability Dashboard

A web platform where a developer uploads package.json and package-lock.json, the platform lists every direct and transitive package, checks each exact version against published advisories, and reports what is affected, how severe it is, and which version fixes it.

Questions the platform answers

  1. Which dependencies does this project use?
  2. Which have known vulnerabilities?
  3. How serious are they?
  4. Which versions are affected?
  5. Is a fixed version known?
  6. What should be updated first?

MVP scope

  1. Sign in and manage scan projects
  2. Upload and validate npm manifest + lockfile
  3. Parse exact direct and transitive versions
  4. Query OSV, match versions to affected ranges
  5. Dashboard, finding details, scan history
  6. Export report; evaluate on a controlled test set

Ground rules

  1. Detects known, published vulnerabilities only; it cannot prove a project is secure.
  2. Never executes or installs uploaded code.
  3. An advisory flags a package only when the installed version is inside its affected range.
  4. Missing severity or fix data is shown as Unknown / Not provided, never invented.

Try it

Open the live demo

The demo runs the real parsing and version-matching logic in your browser against six controlled test projects with genuine npm lockfiles, or against a lockfile you upload. The Evaluation page re-runs all test cases and compares results with an independent check made with npm's own semver library.

High-level architecture

A modular monolith: one Express backend with separate modules for auth, projects, scanning, matching and reporting, backed by PostgreSQL through Prisma.

Request path

  1. Developer uses the React interface.
  2. Frontend sends authenticated requests.
  3. Backend validates the request and checks project ownership.
  4. Scan orchestrator receives uploaded files.

Scan path

  1. Parser extracts package names and exact versions.
  2. Matching engine queries OSV and tests each version against affected ranges.
  3. Backend stores scan, inventory and findings.
  4. Frontend shows results and generates the report.

Security controls on the platform itself (§13)

ThreatControl
Malicious uploadJSON only, 5 MB limit, defensive parse, never install or execute
Cross-user data accessOwnership check on every project, scan, finding and report route
Credential theftPassword hashes (bcrypt/argon2), secrets in env vars, no tokens in logs
OSV outage or slownessTimeouts, retry with exponential backoff, scan marked partial with unchecked packages listed
Untrusted advisory textEscape all OSV and package metadata before rendering

End-to-end scan workflow

The path from sign-in to downloadable report. The live demo runs exactly these steps and shows its progress against them.

flowchart TD
    A([Start]) --> B[Developer signs in]
    B --> C[Create or select a project]
    C --> D[Upload package.json and package-lock.json]
    D --> E{Files valid and supported?}
    E -- No --> F[Show validation error]
    F --> D
    E -- Yes --> G[Create scan record]
    G --> H[Parse dependency files]
    H --> I[Extract package names and exact versions]
    I --> J{Dependencies found?}
    J -- No --> K[Mark scan as empty or invalid]
    J -- Yes --> L[Query OSV for each package]
    L --> L2{OSV responded?}
    L2 -- Timeout --> L3[Retry with backoff]
    L3 --> L
    L2 -- Yes --> M[Receive advisory records]
    M --> N[Match installed versions to affected ranges]
    N --> O[Normalize and classify findings]
    O --> P[Save dependencies and findings]
    P --> Q[Calculate summary and risk indicators]
    Q --> R[Display dashboard and finding details]
    R --> S[Generate downloadable report]
    S --> T([End])

Projects

Evaluation on the controlled test set

Each case uses a real npm lockfile. Expected results were computed separately at build time with npm's official semver library against the same advisory snapshot; the browser matcher must reproduce them.

Matcher verification

For the thesis, report detection coverage as detected expected findings ÷ expected findings, and false positives as findings raised on the patched and no-match cases. Describe the sample size honestly; six cases show the method works, not population-level accuracy.
